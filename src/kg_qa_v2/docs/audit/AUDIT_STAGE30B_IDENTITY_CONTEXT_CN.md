# Stage 30b 审计：身份候选与相关实体分层

## 目标

修复 Stage30a 将“名称身份匹配”和“资料内容相关匹配”混在同一候选集合的问题。

## 实现内容

### 1. 图谱搜索结果分层

文件：

`src/rag/service/graph_discovery_service.py`

保留原有当前领域、已发布状态和多词证据召回能力，但新增两组返回结果：

- `identity_items`：名称、别名、规范化名称、限定名称、层级路径匹配。
- `related_items`：描述、标签、属性或来源证据匹配。

旧的 `items` 字段继续保留，兼容已有图谱搜索接口。

### 2. QA 图谱适配器分层

文件：

`src/kg_qa_v2/graph_adapters.py`

实体解析只消费 `identity_items`；相关实体不会进入实体对齐，也不会触发“存在多个候选”的澄清。

### 3. 候选模型分层

文件：

`src/kg_qa_v2/entity.py`

候选增加：

- `candidate_class`：`IDENTITY` 或 `RELATED`
- `identity_score`
- `context_score`
- `related_entities`

文件：

`src/kg_qa_v2/pipeline.py`

流水线保存相关实体，但实体对齐只使用身份候选。

### 4. 已发布实体与证据解耦

已发布节点是否存在由身份字段决定，不再要求节点必须有属性或来源证据才能参与身份解析。

因此：

- 节点名称匹配但暂无属性证据，仍可以先完成实体链接；
- 后续只在回答具体属性时判断证据是否足够；
- 描述或证据中提到某名称的其他节点，只作为相关实体，不会被当成用户目标。

## 验证结果

### 智能光学实验室

身份候选：

- 418智能光学实验室

相关实体：

- 420智能光学成像课题组

QA 实际回答：

`418智能光学实验室位于物理学院 · 南楼 · 四层。`

未触发错误澄清，实体对齐耗时约142 ms，总耗时约1.27 s。

### 财务部

身份候选保留两个同名节点：

- 行政楼 · b座 · 一层 · 财务部
- 行政楼 · b座 · 二层 · 财务部

首次提问进入澄清；同一会话继续输入“二楼的”后，实际回答为：

`财务部位于行政楼 · b座 · 二层。`

### 发布状态与证据边界

新增测试验证：没有属性证据的已发布节点，只要身份字段匹配，仍可完成 `LINKED`；相关实体不会制造身份歧义。

## 审计结论

Stage30b 已完成身份候选与相关实体分层。当前还没有接入向量身份索引；后续接入向量时，身份索引只能使用名称、别名、类型和层级路径，描述、事实和来源证据继续放在相关内容索引中。
