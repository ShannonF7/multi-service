
# Stage 23 单候选、无证据和 SSE 热修复审计

## 问题根因

### 1. 单候选被错误澄清

候选搜索已经限制在当前领域的已发布图谱，但实体对齐仍要求：

- 高分；
- 特定 match_type；
- 或非常高的置信度。

因此“418智能光学实验室”虽然最终只有一个候选，但若 match_type 为 weak/contains 且分数低于旧门槛，会被标记为 AMBIGUOUS。前端去重后只展示一个候选，造成“只有一个候选却提示多个”的矛盾。

### 2. 无证据仍调用答案模型

流式链路原先在 evidence 为空时仍调用答案模型，只是最后不校验引用。模型可能生成无来源的内容，例如直接回答“位于四层”，同时消耗几十秒。

### 3. A 端首帧被缓冲

B 端和 A 端虽然有 SSE，但代理/反向代理可能在首个小帧达到缓冲阈值前不推送给浏览器。页面因此长期停留在“已发送，正在启动小V……”。

## 修改内容

### 实体对齐

当满足以下条件时自动绑定：

- 当前领域已发布候选集中只有一个候选；
- 分数至少为 0.55；
- 当前节点范围没有冲突。

这不会把空候选或极低分候选强行绑定，但不会再把唯一的有效候选错误地交给用户澄清。

### 证据约束

同步和流式两条答案链路统一处理：

- 非闲聊且没有 Evidence 时，不调用答案模型；
- 直接返回“当前领域的已发布图谱暂未返回足够的可核验资料”；
- 不生成无来源答案；
- 流式答案模型最大输出限制为 256 token；
- 有证据时继续使用引用校验。

### 简单位置问题的快速答案路径

已确认节点且图谱已经返回层级/位置证据时，LOCATION/HIERARCHY 不再调用答案模型重新组织，而是直接把图谱证据分段并带上 E 标签输出。这样可以避免简单问题等待本地模型几十秒，同时答案仍然受证据约束。

### 图谱层级证据

实体对齐后将候选的已发布层级路径写入 QuerySpec 约束，并生成：

“节点的层级位置为：上级 · 上级 · 当前节点”

作为图谱 Evidence，保证“位于四层”这类回答有实际证据可引用。

### A 端 SSE

- 首帧增加 SSE 注释填充，降低代理缓冲导致的延迟；
- 设置 keep-alive；
- 页面提交后立即显示“已接收问题，正在读取会话上下文”阶段，而不是停留在静态等待文案。

## 关于向量匹配

当前 QA 的已发布实体召回入口仍是 PublishedEntity 图谱上的名称、别名、描述和标签匹配，不是向量召回。项目中确实已有 G3 entity embedding 表和向量召回代码，但它面向 semantic_nodes 增长/抽取链路，并不能直接证明节点已经发布；直接复用会破坏本问答链路的“当前领域 + 已发布图谱”边界。

因此本次没有把这个内部向量索引强行接入 QA。后续应单独建立 published entity embedding 索引或提供 published-only vector gateway，再采用“精确/别名 → BM25/关键词 → published-only 向量召回 → 层级和位置对齐”的混合策略。向量只负责扩大候选召回，不直接决定绑定。

## 行为边界

如果唯一候选分数低于 0.55，或与当前节点范围冲突，仍会要求确认。这是为了避免把完全无关的模糊词直接绑定到节点。

如果图谱确实没有返回位置、层级、描述或关系证据，系统现在会明确告诉用户证据不足，不再让答案模型猜测。
