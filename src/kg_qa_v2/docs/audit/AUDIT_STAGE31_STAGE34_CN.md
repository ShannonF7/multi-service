# KG QA V2 Stage31-Stage34 中文审计

## 审计范围

本轮覆盖 Query Decomposition、Active Entity State、Task Skill/FactSkill、属性感知 GraphTool，以及事实答案与证据绑定。

## 输入与输出

- 输入：当前领域、会话历史、用户问题、已解析实体、已发布图谱范围。
- QuerySpec 输出：保留兼容字段 `attribute`，新增 `requests[]`，每一项包含 `request_type`、`attribute`、`surface` 和约束。
- 会话输出：在原有实体记录之外保存 `entity_states`，包括节点 ID、名称、领域、层级路径、节点类型和最近关注点。
- FactSkill 输出：结构化 `claims[]`，每条声明包含请求类型、状态、文本、值和 `evidence_ids`。
- API 输出：答案、引用、claims、证据、处理过程和阶段耗时保持统一返回。

## 逻辑审计

1. 多属性问题先拆成多个独立请求，再由 Plan Compiler 生成 FACT 计划，避免把“管理员”和“联系方式”合并成一个模糊属性。
2. 后续代词问题读取会话中的 active entity，并在当前领域的已发布图谱内继续查询。
3. FactSkill 只查询已解析节点的属性事实和相关关系；图谱节点详情、层级和图片证据不会被当作管理员事实。
4. 每条事实声明只允许引用自己的证据 ID。没有证据时输出 `INSUFFICIENT_EVIDENCE`，不补写模型猜测，也不挂载无关引用。
5. 现有 Graph/Text/Image 资源仍作为工具层使用，本轮没有扩大为自由 Agent 循环。

## 安全与边界

- 查询继续受当前领域和已发布状态限制。
- 不接受模型自由 Cypher；图谱操作由代码计划和参数化查询完成。
- 会话只保存必要的实体状态，不把模型私有思维链写入会话。
- 当前属性查询实现先读取已发布节点详情，再在服务层按属性和关系过滤；功能正确，但后续可改为数据库侧直接过滤以减少查询开销。

## 测试记录

- `pytest -q src/kg_qa_v2/tests`：103 passed，1 个既有 Pydantic 弃用警告。
- `compileall`：通过。
- 真实接口冒烟：第一问“智能光学实验室在哪里？”返回位置及图谱证据；第二问“它的管理员是谁？有联系方式吗？”成功承接会话并进入 FACT 阶段。
- 真实数据结果：当前节点未返回管理员或联系方式事实，因此两条 claim 均为 `INSUFFICIENT_EVIDENCE`，引用为空，符合“不无依据生成答案”的约束。

## 结论

本轮链路已闭合到“问题拆分 → 会话实体承接 → FactSkill → 属性查询 → 声明级证据绑定”。后续若业务确认管理员信息应该存在，应优先检查该节点的已发布属性/关系入库结果，而不是放宽答案生成规则。
