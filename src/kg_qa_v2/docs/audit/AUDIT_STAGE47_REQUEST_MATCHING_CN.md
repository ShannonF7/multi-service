# QA v2 Stage 47 审计报告：请求语义匹配与属性/关系别名

## 变更目标

本阶段把“用户请求”和“实体已有信息”的匹配收敛为结构化请求，不再让答案模型自行猜测属性是否存在。

## 输入与输出

输入：

- 用户原始问题；
- 已完成的实体候选/上下文；
- 当前问题是否包含图片。

输出：

- QuerySpec.requests[]，例如 LOCATION、VISUAL_APPEARANCE、ATTRIBUTE(email)；
- 图谱查询使用的属性/关系别名集合；
- 轻量模型是否需要介入的判定。

## 逻辑审计

1. request_catalog.py 集中维护请求语义规则和属性别名。
2. slots.py 将同一问题拆成多个独立请求；“东门在哪里？长啥样？”会得到 LOCATION + VISUAL_APPEARANCE。
3. router.py 只有在请求目录覆盖当前问题的每个问句片段时才走 Fast Path；未覆盖的自然语言表达不会被静默当作已理解。
4. understanding.py 对未覆盖表达保留轻量结构化模型路径。
5. graph_adapters.py 使用属性别名查询已发布节点的事实和关系。
6. answering.py 只根据返回的证据回答；匹配不到时返回信息缺失，不用无关证据补答案。
7. 上传图片识别问题在请求解析中优先生成 IMAGE_IDENTIFICATION，不会同时误生成普通 IMAGE_RETRIEVAL。
8. 多个请求共存时，目标实体按关键词在原问题中的实际位置提取，避免把“东门在哪里？长啥样？”的目标污染成“东门在哪里”。

## 边界与未做事项

- 规则目录不是实体名称白名单，不包含“东门”等具体节点，因此没有针对单个实体的答案硬编码。
- 未覆盖的同义表达会进入轻量模型；轻量模型只负责结构化理解，不负责判断图谱中是否存在属性。
- 当前属性别名仍需随着实际图谱字段持续补充，但新增别名只需要修改目录，不需要改检索和答案流程。
- UNKNOWN、无证据和实体不存在仍由后续实体解析/检索阶段区分，不能仅凭请求解析阶段下结论。
